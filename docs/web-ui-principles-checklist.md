# Web UI revamp checklist

Tracks the original Orchestrator Principles list, grouped. Baseline findings are in
[web-ui-audit.md](web-ui-audit.md). Status: `[x]` done, `[~]` partly done, `[ ]` not started.
"Done" means implemented and covered by a test or verified in code. Pages were also checked in headless Chrome
(360, 390, 430 and 1300-1440 px, light and dark); nothing has been tried on a real phone or with real users.
The pipeline itself (plan, build, test, review) runs end to end under test: offline in the normal suite, and live
against a free model on request (see `docs/build-test-commands.md`).

## A. Getting started

- [~] **On-ramp / wizard / checklist, minimum steps to the aha moment.** Setup checklist, FAB and panel exist (required vs optional). Time to first job is not measured or shortened.
- [~] **Describe the app in my words, then answer clarifying questions.** New-project flow asks short questions and writes a brief. Job planner questions show only after planning starts.
- [x] **Choose platforms early on a new project.** The new-project questions now ask what you're building for as a multi-select (iOS, Android, macOS, Windows/Linux, web, backend, CLI/library) or "Not sure: recommend for me". The choice goes into the product brief (an undecided choice tells the AI to recommend with reasons), and the finish page lists what each platform needs next. Works in the terminal flow too.
- [x] **Wizard examines current project state and says what's missing.** Tools > Check-up: stage (getting started / building / with testers / released), "n of 10 in place", one highlighted next step, and every item with why and a fix: brief, platforms, AI instructions, git + remote, features, tests, CI, tester delivery, releases, KPIs. Fixes are a pre-filled new job, a link to the right page, or a command to copy. It checks product state; tools and keys stay in the setup checklist.
- [x] **Easy login.** Google, Apple, GitHub or access token.
- [x] **Set up machines and LLMs easily.** Configuration > Machines and Models add, edit and remove them. A planned job that can't start now says why on its page, before you approve it (no machine, limited to a machine that's gone, models no machine runs, low disk), with a link to the fix. The checks mirror the scheduler's rules and share its code.
- [~] **Any main coding language.** Stack detection and language bar. Device logs and the simulator visual check are now offered only when the project builds an app (Xcode, iOS/Android folders, an app id or remote logs). Still iOS/Firebase-shaped: the tester delivery and build/distribute scripts, and the setup wizard's Xcode steps.

## B. Describing and steering work

- [x] **Feature/area of focus is clear and prominent on top.** Job page leads with a status hero: state, reason, one primary action.
- [x] **Info goes general -> detailed, actionable first.** Hero, then Progress, Changes, then docs, links, tasks, runs, logs, raw JSON.
- [x] **No redundant CTAs on one screen.** Job page: one primary action, one menu, each action once. Home: one New job per viewport, no menu of actions (they live on their own pages). Guarded by tests.
- [x] **Statuses made clear (one vocabulary).** Job page, home and jobs lists all use the server's `state` (label, reason, tone, next action). Duplicate emoji vocabularies and banners removed.
- [x] **Express intent; if no strong opinion, LLM recommends.** New job asks only what each kind of work needs, matching the terminal flow: **Bug** (what's wrong, repro steps, expected result, then your latest logs to tick plus uploads of logs and screenshots, and a Sentry/Jira link); **Feature** (what it should do, anything specific, a ticket link); **Design** (what you're designing, look and feel, uploaded images/PDF/.fig/HTML and a Figma pick or link); **Tests** (area and specific parts); **Quick change** (one box). For features and designs the planner is always told to choose conventional defaults for anything left open and record each as an assumption (shown on the job page as "What the AI assumed"); the earlier "You decide the details" checkbox was removed because it was unclear. Uploads are limited to 25 MB and common image, document and log types.
- [x] **Easy to tweak / course-correct.** Revise plan (AI re-plan), Run fix, Still broken?, model override, and now direct edits to the plan: on the job page you can edit a task's title, details, "done when" and files, add a task, move one up or down, or remove one. Finished tasks are locked, a running job must be paused first, and removing or moving keeps completed-task numbers and test-case links consistent.
- [x] **Talk to the LLM directly, tied to the job.** "Ask about this job" thread on the job page; messages are stored in the job file. Read-only: it advises, and Revise plan / Run fix act. (The old Ask AI action started a fix run; removed.)
- [x] **Organize features with no overlap (discrete elements).** Features page: create/edit/delete, group jobs under a feature (job menu: Move to feature), roll-up progress. Overlap warnings when two features claim the same code paths, or two in-flight jobs on different features change the same file. New job has a Feature field, and the planner is told the feature's purpose, owned paths and dependencies, and which paths other features own. Not yet: auto-suggesting a feature.
- [x] **See how pieces fit the overall picture.** Features > Map: features laid out in layers (foundations on the left, what builds on them to the right) with dependency lines, status, job progress, "waiting on" for unfinished dependencies and overlap flags. Dependencies are set by hand in the feature form; circular ones are rejected. Not yet: dependencies inferred from code, or a view of jobs inside the map.
- [x] **Mark features complete (knowing they're never fully done).** "Mark complete" records when; attaching new open work reopens the feature and says so.

## C. Running jobs and control

- [x] **Start / stop / pause.** Start and Run now exist. The hero's Stop is now "Pause" (stops the worker; Resume continues from the next task). Other run views still say Stop.
- [x] **Know job states; resume or delete.** Reviewed jobs with no PR now end with "Mark complete" in the web UI (before, the only option was "Open in console"). Resume from the primary action or menu. Delete is now a real server action (`discard`): reverts the job's changes, deletes its AI branch, archives it. It previously only opened the console.
- [x] **Easy to revert.** Whole-job discard, and now per task: the worker commits each finished task by itself, and the job page offers Undo on the latest finished task (a git revert, so history is kept; it refuses on the wrong branch, with uncommitted changes, or on a conflict, changing nothing). Earlier tasks can be undone one after another, newest first. Jobs run before this change have no per-task commits and only offer whole-job discard.
- [x] **Changes made clear.** The Changes card lists each changed file; open one to read its diff inline (green/red lines, large or binary files handled), and the Scope check flags what went beyond the plan. Orchestrator's own state files are not listed as changes. Not yet: attributing each change to the task that made it.
- [x] **Easy to fix bugs I find.** New job → Bug fix (repro steps, logs, uploads), "Still broken?" on a job.
- [x] **Handles everything; comes to me only with critical questions.** There is one list of jobs on Home. A job that needs you (a question, a plan or design to approve, a review, a failure) is just a job in an earlier status: it sorts first, its status says what it needs (for example "Approve plan"), and the whole row opens the job, where the next step is the one primary action; "Needs you" is also a filter. The count is on the Home nav item and the tab title. Other projects' waiting jobs are one line under the list, and  (This replaced a separate Inbox page and then a separate "Waiting on you" card, both of which duplicated the job list.) Not yet: notifying when a job moves into "needs you" without a run (only run changes notify).
- [x] **Notifications when done or problem.** Three channels: (1) browser alerts (sidebar button) for any job that newly needs you and for runs that finish or fail, firing even in a background tab; (2) Slack-compatible webhook (Configuration > Slack & chat alerts) sent by the web server for the same events, so it reaches your phone with the tab closed, with a link back to the job; (3) the worker's existing email and macOS alerts. Limits: the webhook watcher runs only while the web server runs, and covers the active project only; no native mobile push.

## D. Testing and quality

- [x] **TDD and thorough testing (unit, integration, test cases).** Job page has a Test cases card: covered / planned / no test / manual, split by unit, integration and UI, with steps, expected result and where each test lives, and a warning when automated cases that are due have no test. The Tests page lists the whole project's case library by area with status filters. Coverage is read from the code (an assigned test exists, or a test carries the case id), not from what the model says. Not yet: running a single case from the UI, or a test-first gate that blocks building until tests exist.
- [x] **Anti-gold-plating (refactor pass).** Job page > Scope check compares the diff with the plan and flags: dependency or build-file changes (high), new files and changes to files the plan never mentioned (medium), code outside the feature's own paths (medium), and a change much bigger than its task count suggests (about 400 added lines per task). Tests for planned files, lockfiles and runtime files are not counted. Each finding can be accepted as in scope (remembered on the job), and "Create a job to trim it" opens a pre-filled job listing what to revert or justify. When the next step is merge or complete, the hero warns and links to the check. It is a prompt to look, based on file lists and sizes, not a judgement of code quality; it does not read the code for unneeded abstractions.
- [~] **UX heuristics analysis (use ui builder connection).** Expert evaluation against Nielsen's ten heuristics, written up in `docs/web-ui-heuristics.md`: 18 findings fixed (including in-app Help, Undo for deletes, a command palette, plain Configuration names and clearer errors); none left open from this evaluation, though a single reviewer finds only part of the problems. It was done by reviewing rendered pages and code, not through the Figma connection (which links designs to jobs but can't analyse screens), and not with real users. Not yet: an analysis built into the product that runs on a design or on the running app.

## E. Delivery and environments

- [~] **Easy distribution for manual testing and device management.** Delivery page: latest build with testers (version, build, groups, when, which job), "Send current branch", per-job "Send to testers" for reviewed work, earlier builds, tester groups, and a warning if the Firebase CLI is missing. Testers and devices themselves are managed in the Firebase console (linked); the UI can't add or remove them.
- [x] **Handoff once built to try with a group.** Send to a Firebase tester group from the Delivery page or a job. Paste the group's Firebase invite link once (Configuration > Tester builds) and Delivery shows it with a Copy button, so anyone can join and install without being added one by one. The link is Firebase's, not an Orchestrator page; the app does not host installs itself.
- [x] **Versions, branches, what's live/prod.** Delivery > Live treats the base branch as production: its newest commit, the last release tag, and how many changes are not yet released. Next to it: what testers have, and what is ready to ship. Not yet: named environments beyond "live" and "testers".
- [~] **Good CI/CD.** Delivery > Pipeline shows recent GitHub Actions runs (status, branch, link) and whether the base branch build is passing, and failed, cancelled or timed-out runs have Re-run failed (`gh run rerun --failed`). Needs `gh` signed in; Xcode Cloud is only detected, not read. No way to trigger a workflow from the UI. The re-run was tested against a fake `gh`, not a live repository.
- [x] **Use on mobile and distribute to mobile.** Phone layout verified at 360, 390 and 430 px in light and dark, with no horizontal scroll on any main page: bottom bar plus a More sheet reach every page, long job-page sections fold, and the alerts and invite link work from a phone. Distribution to phones is Firebase (send a build, share the invite link). Not tested on a real phone or tablet.

## F. Integrations and measurement

- [x] **Integrate with Jira and similar.** Connections page, link picker, update log.
- [~] **Connections to other product-creation tools.** Figma, Trello, Sentry. Nothing further.
- [~] **KPIs and analytics setup (2-3 platforms).** Tools > Measure: connect Mixpanel, Amplitude or PostHog (US/EU, key stored but never shown) and verify with a test event; define KPIs per feature (event, target, direction, unit); export a tracking plan to `docs/analytics/tracking-plan.md`. Jobs created under a feature are told to emit its KPI events through the project's analytics layer and add a test for each. Caveats: the test-event calls follow each provider's documented ingestion API but were only checked against fakes, not a live account; it does not read numbers back from the provider.
- [~] **Build-measure-learn.** Each KPI has a learning log: log a result by hand with a decision (keep / iterate / drop) and a note; the page shows latest vs target, trend and on-track / behind, and feature cards summarise their KPIs. A KPI that is behind offers Plan an improvement: a feature job pre-filled with the KPI, the gap, the last decision and a request for the smallest change plus how to know it worked. Not yet: results pulled automatically from the provider.
- [ ] **Experimentation / A/B (future).** Deferred by design.

## Housekeeping

- [x] Debug "Original Home/Jobs" toggles and their duplicate layouts removed.
- [x] Fixed the carried-over failing test (its fixture lacked the test cases plans now require).
- [x] Inline `style=` attributes in `app.js` cut from 97 to 50 by replacing repeated spacing with utility classes. The rest are dynamic (progress widths) or one-offs.
- [x] Per-job visual QA: a visual check started from a job is tagged with it and only that job's page shows its screenshots. Also fixed: the check list looked for folders the script never creates, so the card could not have shown real results; screenshot URLs are now strictly validated (hardening; the old path handling was not shown to be exploitable).
- [x] Accessibility pass, measured with a Chrome DevTools audit over 12 pages x phone/desktop x light/dark: fixed contrast failures (light-theme accent, warn, ok, bad and muted colours; white text on amber badges), a duplicate icon id, an unlabelled chat box, small tap targets, and no visible focus ring on links. Added a skip link, a page title that updates per page (with the inbox count), focus moved to the page heading on navigation, and removed `aria-live` from the whole page. Audit result: 0 issues in overflow, names, labels, contrast and ids. Not covered: a real screen reader, keyboard-only walkthrough of every dialog, and the terminal pages.
- [x] Verified in a browser (headless Chrome via DevTools) at 360-430 px and 1300-1440 px, light and dark, for the main pages. Found and fixed: on phones the Lock session and Notify buttons were off-screen, and Tests, Git, Delivery, Measure, Check-up and Connections had no way in (now a "More" sheet in the bottom bar). Not tested: a real phone, tablet widths, landscape, the terminal/run pages, and the sign-in screen.

## Working well with the LLM (one living product doc)

One short document, `docs/product/prd.md`, replaces the six product documents and the periodic review. It has five sections, in the person's own words:
**Pitch** (as if explaining to a friend, plus what it is built for), **Who it's for** (an ideal user or situations; "not sure yet" is fine), **Core features** (optionally as user stories), **Look and feel** (a description, uploaded designs and sketches, Figma items) and **Not this** (optional). "Not verified" means the code and prompts are in place but how well any given model follows them has not been measured.

- [x] **Say it simply, and only what you know.** The Product page opens on the Pitch with a prompt to write it the way you'd tell a friend. Every section is optional. For a project that already has code, "Draft it from my project" reads the README, notes, manifests, layout and recent commits and proposes a first version for you to correct (never inventing "Not this"). New projects get the document filled in from the wizard's answers.
- [x] **Import PRD.** Drag a file onto the drop zone (computers) or choose one: a markdown, text, Word or PDF file (PDF needs `pdftotext`), or pasted text, is rearranged into the five sections keeping the person's wording, and shown as a diff before anything is saved.
- [x] **Look and feel from designs.** Upload images, PDFs, `.fig` or HTML files (kept in the repo under `docs/product/designs/`, images shown as thumbnails), paste a link, or pick an item from a connected app such as Figma (its link and image are added). Not verified: how well models use the images.
- [x] **Every AI reads it.** The planner, builder, debugger, reviewer and plan verifier are each handed the filled-in sections in a form that suits them (builders get less and are told to use `clarification_needed` rather than guess; reviewers and the verifier flag work that serves no listed feature, builds something under "Not this", or departs from the look and feel). Nothing is added until something is written. Not verified: how closely any given model follows these rules.
- [x] **A living document.** When a feature or design job (or any job where the person answered questions) finishes, the model is asked whether what it showed changes what the document says. It edits only when something clearly changed, keeps the person's words, and the edit is refused if it empties a section, removes anything under "Not this" or cuts the document down. Runs on the job's own allowed models, so a free-only job stays free-only. Tested end to end through the real worker.
- [x] **Slow model work can't time out the page.** Drafting and importing run in the background and the page checks back every 1.5 s, with a spinner and a timer. A reply in the wrong format is asked for again once. (A quick tunnel closes any one request after about 100 s; a 70 s draft on a larger project had made that a real risk.)
- [x] **Visible, reversible and optional.** The document can be edited by hand any time, section by section. Every change (yours, the AI's, an import, a restore) is a version in a history with a diff, and any version can be restored (a restore is itself a version, so nothing is lost). An automatic update is announced with a banner on Home and the Product page, a toast and, if turned on, a browser notification, each with See what changed and Undo. A switch turns automatic updates off (on by default). Model calls that only answer a question (job chat, Help me, Import, Draft, and the automatic update) run in an empty scratch folder, so an agentic model can't write into the project or rewrite the document behind the history's back.
- [x] **Earlier projects carry over.** A project with the old brief and use-case documents has them folded into the new document the first time it is opened; the old files are left where they are.
- [x] **Vertical slices.** The feature planner is told the first task must leave something running end to end, and each plan is checked (a foundations-only first task, a first task with no acceptance criteria, or data, service, screen layering sends the plan back once; if it still looks layered it is kept with a visible "Plan check"). The check reads wording and can be wrong in either direction; it never blocks a plan.
- [x] **Implement, test, inspect, iterate.** Per-task build and tests, fix loop, reviewer, test-case coverage, scope check, and the combined check across a feature's jobs.
- [ ] **Not done: a separate product review job.** It was removed with the six documents: a document that keeps itself true made the periodic review and its reminder redundant. Drift between the document and the code is only caught when a job's own information contradicts the document.

## Working with several LLMs and different machines (added later)

- [x] **Verify that separately built pieces work together.** Features > "Check together": merges all of a feature's job branches onto the base branch in a throwaway git worktree (your checkout is never touched) and runs the project's build and test commands on the result. It reports which branches conflict and in which files, or that the combination fails the build or tests even though each branch passed alone, and it says when a branch or the base has moved since the last check. Run on demand; it is not triggered automatically after a merge. Tested with real git repos and in the dummy project end to end.
- [~] **No overlap between pieces built by different LLMs.** Features own code paths, and the page warns about two features claiming the same paths or two in-flight jobs changing the same file. It warns; it does not assign non-overlapping slices or stop a clash.
- [~] **Find compatibility problems early.** Check-up > "Will this computer build it?" probes before anything runs: the programs the build and test commands start, the AI command-line tools the chosen models need, GitHub sign-in, free disk, and for Apple app projects Xcode selection and first-launch setup, a usable simulator (the same recognisers that explain a failed build, such as an out-of-date CoreSimulator) and a machine marked able to build with Xcode. Failures that block work also appear as "This job can't start yet" on a planned job. Not covered: other stacks' toolchains beyond the commands' own programs (Android SDK, emulator), and detecting that an IDE has the simulator locked.
- [ ] **Help with requirements that adapts to the kind of user.** The question flow is the same for everyone. The user types are open-ended and depend on the app; they need to be defined before this can be built.

## Documentation (added later)

- [x] **A central place for the project's documentation.** Docs (sidebar, under Learn & improve): the product requirements, a page for every feature and every job (including finished, archived ones), and the project's own `README`, `AGENTS.md`/`CLAUDE.md` and `docs/**/*.md`, with search and a "Download everything (.md)". A job's page covers what it is, assumptions, decisions you made, the architect's check, tasks with their done-when lines, how it is tested, what was built, files changed, the review and linked tickets. A feature's page covers what it is, who it serves, where it lives in the code, every job in it and how it is measured. Linked from each job's menu and each feature's menu.
- [x] **Always true.** Job and feature pages are composed on request from the job files and the feature store, so they cannot drift and add no files to the repository. Project files are shown as they are in the repository (only README/notes and `docs/` markdown; designs, dependencies, tooling folders and hidden files are excluded and cannot be requested).
- [~] **Not durable.** Because job and feature pages are composed, they exist only while the job files do, and the job files and the build, test and review logs live in `.orchestrator/` (not committed). Download the export if a record needs to live in git. A job's raw brief, build and test logs are still only on the job page.
- [ ] **Not done: documentation that is kept up to date by the AI the way the PRD is** (a written-prose page per feature). Today's pages are assembled facts, not narrative.
