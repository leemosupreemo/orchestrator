# Two-Mac verification MVP implementation plan

**Goal** — A feature job can use two project-authorized Macs to obtain its required test evidence sooner, or obtain evidence available only on the helper. One owner reports the verdict. Losing a laptop mid-check cannot turn an incomplete run green.

**First supported workload** — The owner runs the existing build and main tests. At the existing extra-test boundary, two explicitly independent per-job checks can run concurrently, one per Mac, against the same source tree. For the DAoC pilot, use protocol and server-profile suites if their maintainers confirm both run from a clean checkout. If those suites already run in the main command, move them into named checks during pilot configuration and verify identical coverage. Never count running the same suite twice as a gain.

**Scope decision** — Start with this two-check fork and join. It exercises capabilities, placement, source identity, recovery and evidence collection without changing the order of the main build or the ownership of code changes. Overlapping a Unity build with tests, transferring build products for device checks, parallel AI editing, arbitrary dependency graphs and cross-run result caching are follow-on work. The first pilot measures the speedup available from this narrower boundary.

**Implementation workflow** — Execute milestones in order using the executing-plans workflow. For each milestone, add its regression cases, observe the failing focused test, implement, rerun and review the scoped diff as one commit.

## Current status

Job runs support local observation and opt-in assistance at the extra-test stage. The assistant uses one configured SSH helper, exact Git candidates, manually supplied calibration, durable attempt records and local fallback. Both marked checks must pass in assist mode. Tests exercise overlapping checks, lost helpers, stale source and missing evidence. The owner checks source identity at the end of the extra-test stage.

The remaining work covers the final delivery commit check, resuming an interrupted invocation from the builder, automatic calibration and queue estimates, the compact progress display, and the live Pro-to-Air pilot. Follow [assisted verification setup](../../user-guide.md#try-assisted-verification), [helper recovery](../../job-recovery.md#verification-helper-recovery), and the [focused tests](../../build-test-commands.md#test-suite) for the current behavior.

## Existing entry points and constraints

- `orchestrator/scripts/schedule_job.py` assigns one task group, machine and model. Keep that assignment as the job owner. Verification helpers run deterministic commands and do not consume a model or inherit the builder’s model eligibility check.
- `orchestrator/scripts/run_builder.py` calls `run_build_and_tests`. In `orchestrator/scripts/run_build_and_tests.py`, extra commands run after successful main checks. `orchestrator/test_commands.py` already parses named commands, tiers, requirements, timeouts, retries and result files. Reuse those semantics and the normal result parser.
- Verification can occur before `orchestrator/scripts/worker_run.py` commits the builder’s final edits. Sending the current branch tip alone can test yesterday’s code. An immutable candidate is a prerequisite for dispatch.
- Use project Git for source and shared job state. Keep detailed logs, timing history and leases on the participating Macs. Firestore receives no new project content. A private helper protocol must negotiate its version before dispatch. Follow the repository release rule if implementation changes the shared job or sync format.
- Use a project-level opt-in with modes `off`, `observe` and `assist`. Existing projects default to `off`. Explicit project and job machine restrictions apply, including a job limited to `local`. A helper must be explicitly enabled for that project and permitted by the job.

## Milestones

### 1. Define a verification unit and establish the baseline

- [x] Extend the existing extra-command parser with an optional Boolean `parallel_verify`, default false. True means the project owner declares this per-job command independent, required and runnable from a clean source checkout. Reject true on manual or nightly tiers. For the pilot, require exactly two opted-in commands in one contiguous per-job pair. Leave other commands in their original order. Invalid opt-in configuration produces an actionable configuration error.
- [ ] Add `orchestrator/verification.py` to form a verification request from the two parsed commands. Include project identity, job ID, invocation ID, candidate tree, and a digest of each effective command definition including cwd, requirements, timeout, retry policy and result paths. Each invocation gets a distinct ID, including separate builder/debug passes in one job.
- [x] Record per-check runtime and elapsed time from start of the pair to accepted results. In observe mode run the original local sequence. Record a missing prerequisite explicitly.
- [x] Add `tests/test_verification.py` cases for legacy configuration, duplicate names, malformed opt-in, main-check failure, a job override that skips testing, and an exact main/extra command duplicate. Verify observation preserves local order, return values and blocked reporting.

Set `verification_mode` to `observe` in project.json to collect baseline timings. Mark the two independent extra commands with `"parallel_verify": true` and run `orchestrator check-config`. Each run of the pair writes a local JSON measurement beneath the job's output directory at `verification/<invocation-id>.json`. Use `off` to disable measurements. In `assist` mode, the dispatch request binds the check digest to the candidate and project, and the runner requires evidence from both checks.

The current DAoC-Mobile main test command already runs protocol tests, the vegetation integrity check and server-profile tests with a prepared temporary source tree. Pilot setup must preserve the vegetation check and the server preparation step. Confirm the latter works in an isolated checkout before opting it in.

### 2. Establish helper eligibility and an exact source handoff

The Git handoff is implemented in `orchestrator/verification_candidate.py` and exercised with two local clones. It requires a pinned HEAD and an explicit list of job-owned paths. The builder still needs to supply that list and compare the candidate tree against the final accepted tree. Checkouts that need submodule or Git LFS materialization are currently ineligible.

The eligibility evaluator in `orchestrator/verification_placement.py` accepts verification offers only from explicitly enabled SSH helpers with `verification_helper: true` in the project's machine configuration. A report must agree on protocol, repository, disk, candidate availability and the toolchain for the check being considered. `orchestrator/verification_transport.py` and `orchestrator/scripts/verification_worker.py` implement the SSH preflight. The helper matches command digests against its own project config and checks prerequisites in the verified checkout. Version probes currently cover .NET, Python, Swift and Xcode. The protocol has been tested with a subprocess against real local clones and a mocked SSH call. The live Air connection remains to be verified.

- [ ] Reuse `discover_machines.py` to list candidates and the configured SSH probe in `probe_machine.py` to validate the enabled helper. Add a verification handshake for protocol version, repository identity, effective tool version, free disk and capacity. Run the configured prerequisite checks again in the actual checkout. A compatible .NET helper can qualify with zero AI models. Never enroll a discovered computer implicitly.
- [ ] Add candidate creation in `orchestrator/verification.py`. Use an isolated Git index based on the job base and checkpointed work. Include only identified job edits, additions and deletions. Leave the real index, branch and working files untouched. If ownership of dirty inputs is ambiguous, run both checks on the owner and explain the fallback. For a clean committed candidate, reuse its commit directly.
- [ ] Publish a unique temporary candidate ref in project Git. Each runner fetches and verifies the exact commit and tree into a separate worktree. A checkout missing required submodule or LFS content is ineligible. Compare the verified tree with the tree being accepted before delivery. Any later fix invalidates the evidence. Delete only refs and worktrees owned by this invocation on completion or bounded cleanup.
- [ ] Add `tests/test_verification_candidate.py` with a bare Git remote and two clones. Cover uncommitted job files, deletions, unrelated staged edits, branch movement, fetch failure, local-only policy, old helper software and zero-model eligibility. Assert original HEAD and index remain intact and neither runner silently substitutes another revision.

### 3. Predict when the second Mac earns its place

- [x] Implement a pure placement function in `orchestrator/verification_placement.py`. Inputs are the two checks, eligible machines, queue delays and timing samples. Enumerate eligible assignments including both checks sequentially on one machine. For each machine, start with its queue delay, charge setup once per candidate, then add the durations of its assigned checks and evidence return. The pair finishes at the later machine finish. Use the fastest eligible assignment subject to the pilot threshold.
- [ ] Persist local timings by project, check digest, toolchain, machine and warm/cold checkout. Start with medians of recent comparable samples. Record predictions alongside actuals. With fewer than three comparable observations for a required estimate, prefer local execution when it can supply all evidence. Use explicit pilot calibration runs to seed remote estimates. Keep observed data separate from predictions.
- [ ] Proposed pilot default: use a helper for speed when its predicted saving exceeds both 10 seconds and 10% of local pair time. Choose local on ties. If only the helper can supply required evidence, choose the eligible placement regardless of speed. Refresh eligibility before starting queued work. Enforce one active verification check per machine for the pilot, accounting for competing jobs through the admission check.
- [ ] In `tests/test_verification_placement.py`, model two 60-second local checks and a 5-second helper setup with a 60-second remote check. Expect 65 seconds split against 120 local. Also cover a cold helper taking 130 seconds to prepare, an occupied helper, uncertain estimates, local-only restriction, and a uniquely capable helper. Assert the recorded decision explains each placement.

### 4. Execute once per accepted attempt and recover from interruptions

The worker-side journal is implemented in `orchestrator/verification_attempts.py`. The SSH worker now handles start, status, result, renew and cancel. The detached supervisor claims the reservation once, checks out the candidate, and runs the approved command with the existing retry and result parsing logic. It holds the execution lock through process exit, terminates the process group on cancellation or lease loss, and retains a bounded output tail and result summary for reconnect.

`orchestrator/verification_coordinator.py` persists the owner record before dispatch, reconciles lost replies and restarts using the same attempt identity, sends renewals, and validates the returned check and toolchain. `orchestrator/verification_assist.py` connects it to the builder's extra-test stage, falls back to the owner after infrastructure loss, and requires both checks in assist mode. The builder supplies a local ownership check. It currently starts a fresh verification invocation on a whole-job resume. Reopening an interrupted invocation from the builder, verifying the final delivery commit, collecting calibration automatically and running the live pilot remain open.

- [ ] Add `orchestrator/scripts/verification_worker.py` as a narrow SSH entry point for probe, start, status, result and cancel. Pass structured input over stdin. Resolve a named, approved command and its digest against the helper’s trusted project configuration before execution. A mismatch requires setup. Reuse command timeout, process-group cleanup and existing result parsing. Run the two checks in isolated worktrees even when both land on one Mac.
- [ ] The owner persists an atomic local attempt journal before dispatch. Key entries by invocation, check, candidate, owner generation and attempt ID. The worker atomically reserves its machine slot, deduplicates repeated starts for the same attempt and retains the terminal result for reconnect. Renew a lease while connected. Proposed pilot defaults are a 10-second heartbeat, expiry after 60 seconds, and one infrastructure reassignment. Bound log collection and send only declared result files contained inside the attempt directory.
- [ ] At the extra-check boundary, the owner collects results and applies the existing test failure and flaky-retry semantics. Missing required evidence yields an explicit incomplete/blocked outcome. Only loss of infrastructure triggers reassignment. Reconcile a dropped connection with the existing attempt before retrying. On cancel or ownership handoff invalidate the old generation. After restart resume the journal only for the current owner and unchanged candidate. An old reply cannot finalize a new run.
- [ ] Wire the results through the same build/test return path, review and delivery gates as local checks. Fallback runs preserve the declared required-evidence rule in assist mode. Preserve the command order around the pair. A genuine failing check retains its diagnostics and enters the existing failure workflow.
- [ ] Add `tests/test_verification_attempts.py` using an injected clock and transport. Test duplicate delivery, simultaneous reservation by two jobs, helper sleep, lost acknowledgement after completion, coordinator restart, cancellation, ownership handoff, stale success after a newer failure, and failure to recover any eligible runner. Assert at most one accepted result per check and no pass with missing evidence.

### 5. Prove the normal job path and run the pilot

- [ ] Add `tests/e2e/test_distributed_verification.py` using a throwaway project, bare remote, and two worker processes with separate roots and a fake SSH transport. Drive the real builder entry point. Use a synchronization barrier to prove both checks overlap. Assert identical candidate IDs, distinct worker IDs, evidence from both checks and a single owner verdict. Repeat with a disconnected worker and with the feature disabled.
- [ ] Show one compact run status such as “Verifying on 2 computers · 1 of 2 checks complete”. Expanded details show check, machine, outcome and fallback reason. Count accepted checks once in job progress. Extend `tests/test_run_progress.py` and `tests/test_web_ui.py`. Follow `docs/web-ui-conventions.md` and check narrow screens.
- [ ] Update `docs/user-guide.md`, `docs/job-recovery.md` and `docs/build-test-commands.md` with enablement, eligibility, calibration, recovery, rollback and focused test commands. Run `python3 -m compileall -q orchestrator tests`, the focused verification modules, then `python3 -m unittest discover -s tests`. Validate changed project configuration with `orchestrator check-config`.
- [ ] On an opt-in pilot project, authorize the Pro and Air, confirm the job allows both, and verify helper toolchains. Alternate owner-only and assisted runs on the same revision, with matched warm/cold conditions. Record at least five paired runs per condition. Measure whole-job time to verdict, pair time, machine-minutes, evidence completeness and prediction error. Report individual times and medians. Treat the slowest samples as diagnostic until enough runs accumulate for a meaningful percentile.
- [ ] Pilot acceptance requires identical check coverage and verdicts, one observed overlap, one successful disconnect recovery or explicit incomplete outcome, and no stale evidence accepted. Proposed performance target: at least 10% lower median **whole-job** time on the chosen speed workload with at most 20% more machine-minutes. Report capability-only wins separately. If the checks occupy too little of the job to meet the target, retain observation mode and use the timing breakdown to decide whether overlapping the main build is worth the next increment.
- [ ] Roll back by disabling new assisted invocations, draining or cancelling active attempts and preserving their recorded outcomes. Re-run the local-only end-to-end case. Expand beyond the pilot only after reviewing both correctness and timing results.

## Review focus

| Failure mode | Required proof |
| --- | --- |
| Helper shows online but cannot fetch this project or run its SDK | Capability probe and real checkout tests in milestone 2 |
| Owner verifies a branch tip while a job edit is still uncommitted | Candidate and final-tree identity tests in milestone 2 |
| Busy or cold Air makes the verdict slower | Local baseline and placement fixtures in milestone 3 |
| Sleeping helper replies after another attempt finished | Generation and attempt reconciliation tests in milestone 4 |
| Splitting commands drops a test, changes a gate or counts retries twice | Legacy parity in milestone 1 and end-to-end evidence checks in milestone 5 |

The placement rule borrows earliest-finish scheduling from HEFT and accounts for the cost of moving work. Exact candidate and command identity follow the remote-execution action model. Two checks and two Macs allow direct enumeration of every placement.
